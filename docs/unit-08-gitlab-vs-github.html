8.1 定位與哲學

GitHub 與 GitLab 都「建在 Git 之上」，功能大量重疊——但哲學、託管模式、CI/CD 設計截然不同。 本章從十個面向拆解，最後給選型指南。

GitHubGitLab
核心定位程式碼社群與生態——世界最大開源社群一體化 DevOps 平台——完整生命週期
哲學「平台」：整合第三方、市集生態「單一產品」：全功能內建、一處搞定
背後公司Microsoft 旗下GitLab Inc.（開源版與商業版同源）
主要入口github.com（公有雲為主）gitlab.com ＋ 可自架

8.3 託管模式：自架 vs 雲端（關鍵差異）

GitHub
公有雲為主（github.com）
自架：GitHub Enterprise Server
      閉源、需付費、功能受限
幾乎所有人都用同一朵雲
GitLab
公有雲：GitLab.com
自架：GitLab CE / EE
      CE 完整開源、可免費自架
「自架」是 GitLab 的招牌能力
一句話：需要「程式碼與 CI 完全留在自家伺服器」時， GitLab 自架是主流答案；GitHub 的自架（Enterprise Server）閉源且貴。

8.4 CI/CD 差異深入

GitHub ActionsGitLab CI/CD
內建程度平台功能，在 repo 加 workflow產品核心，原生整合（MR 頁即見 pipeline）
設定檔.github/workflows/*.yml.gitlab-ci.yml
執行機器GitHub-hosted runner + 自架共享 runner + 自架 runner（常見做法）
重複使用豐富的 Actions MarketplaceCI 組件（components）、跨專案引用
深度整合需串接外部服務內建 container registry、環境部署、review apps
上手曲線市集幫你快速拼自己寫較多，但彈性大
觀察：GitHub Actions 靠「巨大市集」取勝（現成 action 一接就好）； GitLab CI 靠「與平台深度整合＋自架 runner」取勝（CI 是產品的一部分，不是外掛）。

8.11 選型指南 · Which to Choose

選 GitHub 如果…

  • 在找開源專案或想參與開源——GitHub 是主場。
  • 想要最豐富的 Actions 市集與生態。
  • 只想用公有雲、不需要自架。
  • 求職 / 作品集曝光。

選 GitLab 如果…

  • 需要完全自架（程式碼與 CI 不出公司）——法規、資安、隱私需求。
  • 想要一個產品搞定 DevOps，少接第三方。
  • 需要細緻的批准規則（免費即有）。
  • 認同開源平台理念。

兩者皆可時

只是「個人用雲端放程式碼」——兩個都免費、都夠用，挑順手的即可。很多人同時使用兩者。

8.12 遷移與並用 · Migration

常見問題：「GitHub 用得好好的，有必要換嗎？」——不一定要換。幾種務實情境：

  • 企業採 GitLab 但個人留在 GitHub：很常見。公司內部資安要求走自架 GitLab，個人作品照放 GitHub 曝光。
  • 遷移工具：GitLab 提供內建的「Import project」可以從 GitHub 直接搬 repo（含 issue、MR、label）。搬過去再檢查 CI 設定即可。
  • 並用策略：開源專案放 GitHub 吸引社群、內部專案放 GitLab 留資料——兩者用同一套 Git 指令，無痛切換。
  • 不要為換而換：團隊工具切換成本很高。除非有明確理由（自架、批准規則、開源），否則維持現狀常是更划算的決定。
務實建議：先學好 Git 與「平台無關」的部分（branch、commit、review 精神）， 再補一層「平台專屬」的術語與流程——你就同時是兩邊的使用者，而不是某一邊的俘虜。

進階真實情境 Worked Example

情境：企業從 GitHub 遷移到 GitLab 的完整流程

一家 50 人公司因資安法規要求「程式碼不出境」，決定從 GitHub.com 遷移到自架 GitLab CE。遷移涵蓋 12 個 repo、CI/CD 設定、Issue 與 MR 歷史。

遷移步驟 · MIGRATION PLAN
# 階段一：環境準備（1 週）
1. 自架 GitLab CE（Docker 部署）
2. 註冊 Runner（Docker executor，tag: company）
3. 設定 LDAP/SSO 整合公司帳號
4. 設定 Protected Branches 規則

# 階段二：Repo 遷移（2 週，逐個 repo）
# 用 GitLab 內建 Import（支援 GitHub 直接匯入）
5. GitLab → New project → Import project → GitHub
6. 授權 GitLab 存取 GitHub repo
7. 選擇要匯入的 repo → Import
# 包含：程式碼、Issues、MR、Label、Milestone

# 階段三：CI/CD 遷移（每 repo 1-2 天）
8. 把 .github/workflows/ 轉換為 .gitlab-ci.yml
9. 把 GitHub Secrets → GitLab CI/CD Variables
10. 調整 Runner tag 與 image 設定
11. 測試 pipeline 綠燈

# 階段四：DNS 與通知（1 天）
12. 更新內部文件中的所有 GitHub 連結
13. 通知團隊新的 clone URL 與工作流程
時間估算：12 個 repo 的完整遷移（含 CI 轉換）大約需要 3-4 週。關鍵瓶頸不在 repo 搬運（內建 Import 很快），而在 CI/CD 設定的轉換與測試。

深入原理擴充

GitHub Actions 與 GitLab CI 的 YAML 結構對比

概念GitHub ActionsGitLab CI
設定檔位置.github/workflows/*.yml（多檔）.gitlab-ci.yml（單檔，可用 include 拆分）
觸發條件on: push / pull_request / schedulerules: if / only / except（隱含 push/MR 觸發）
Job 定義jobs: build: runs-on: ubuntu-latestbuild-job: stage: build（需先定義 stages）
執行環境runs-on: 指定映像或 self-hostedimage: 指定映像（配合 executor）
步驟steps: - run: / - uses: action@v3script: - command（純 shell）
重複使用uses: owner/action@v3（市集）include: project / template / component
密鑰管理Settings → SecretsSettings → CI/CD → Variables
轉換心法：GitHub Actions 的 uses: actions/checkout@v3 在 GitLab CI 中不需要——GitLab Runner 自動 clone repo。主要轉換工作在於把 steps 攤平成 script 列表，並把 on: 觸發條件改為 rules:。

診斷式疑難排解表

症狀可能原因解決方案
從 GitHub Import 後 Issues 沒有全部帶過來GitHub API 有分頁限制，大量 Issues 時可能遺漏用 GitLab 的 Rake task 手動重新匯入，或分批 Import
GitLab CI 的 rules 條件不支援 GitHub Actions 的 cron scheduleGitLab CI 用 cron: 在 only: 或 rules: 中設定，語法不同改用 rules: - if: '$CI_PIPELINE_SOURCE == "schedule"' 搭配專案的 Pipeline schedules 設定
遷移後 clone URL 太長（含完整群組路徑）GitLab 的 project 路徑包含 group/subgroup/project設定 SSH remote（git@gitlab.example.com:group/project.git）比較簡潔
GitLab 的 Container Registry 與 Docker Hub 衝突CI script 中同時 push 到兩個 registry，認證混亂在 CI Variables 分別設定兩組 credentials，script 中明確指定 $CI_REGISTRY_IMAGE 與 Docker Hub URL
團隊成員混淆 MR 與 PR 的術語長期使用 GitHub 的肌肉記憶製作術語對照表貼在團隊 Slack/飛書頻道，過渡期用「MR（即 PR）」括號說明

進階挑戰題

  1. CI 轉換實戰：把以下 GitHub Actions workflow 轉換為 GitLab CI（.gitlab-ci.yml），並說明每個步驟的對應關係：
    GitHub Actions 原文
    on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test
  deploy:
    needs: build
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - run: echo "deploy"
  2. 混合平台策略設計：一家公司同時使用 GitHub（開源專案）與 GitLab（內部專案），設計一個「共用 CI 元件」的方案——如何把 GitLab 的 CI template 在兩個平台間共享使用。
