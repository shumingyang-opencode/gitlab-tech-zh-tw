2.1 術語先導：Project / Group / Subgroup

GitLab 不用「Repository」，改用專案（Project）與群組（Group）：

GitLab 術語GitHub 對應說明
Project（專案）Repository程式碼＋Issues＋CI＋Pages 的容器
Group（群組）Organization組織多個專案、集中管理權限與共用 Runner
Subgroup（子群組）—（GitHub 無對等）群組可巢狀，做出組織樹
Namespace（命名空間）owner 名專案路徑的第一段：group/project 或 user/project
為什麼叫 Project：GitLab 認為專案不只是「程式碼」—— 還含 Issues、CI/CD、容器庫、Pages，所以叫專案比叫 repo 更貼近它「完整產品單位」的定位。
路徑解讀：網址 gitlab.com/team-ai/backend/api-gw 中， team-ai 是 Group，backend 是 Subgroup，api-gw 才是 Project。

2.2 流程一：建立專案

網頁操作 · WEB UI
1. 右上角「＋」→ New project → Create blank project
2. Project name：hello-world（自動生成 slug）
3. Visibility：Private（先選這個，可事後改）
4. 勾選 Initialize repository with a README
5. 可選 .gitignore 樣板、LICENSE 樣板
6. Create project
新手常踩：把 visibility 設成 Public 以為無所謂—— 程式碼會公開給全世界（含未登入者）。不確定就先 Private，之後隨時可改。

2.3 流程二：Clone 到本機

命令 · COMMANDS
git clone https://gitlab.com/USER/hello-world.git
cd hello-world
git remote -v          # 確認 origin
結果 · RESULT
hello-world/
├── .git/          # 版本歷史（本地）
└── README.md      # 剛勾選產生的檔案

2.4 流程三：改檔 → 提交 → 上傳

Git 的日常循環與 GitHub 完全一樣（Git 是同一套工具）：

日常循環 · THE LOOP
git add .
git commit -m "說明這次改動"
git push
習慣養成：commit 訊息寫「做了什麼」而不是「改了檔案」—— git log --oneline 一眼看懂歷史，未來的人（包括三個月後的你）會感謝你。

2.5 流程四：從零推送既有資料夾

本機已經有專案、GitLab 上只有空白專案時：

首次推送 · FIRST PUSH
cd /path/to/my-app
git init -b main                     # 或 git init 後 git branch -M main
git add .
git commit -m "first commit"
git remote add origin https://gitlab.com/USER/hello-world.git
git push -u origin main              # -u 記憶 upstream，之後直接 git push
權限錯誤 403/denied 時：多半是認證問題。改用 SSH（git@gitlab.com:...git） 或確認 PAT scope 勾了 write_repository，而不是把 URL 改來改去。

2.6 Group 群組：組織專案

多個專案該放進群組管理：

建立群組 · GROUP
左上角選單 → Groups → New group
├── Group name：my-company
└── 建立後可在 Groups 內再建 Subgroup
    （如 my-company / frontend）

把既有專案移入：Project → Settings → General
  → Advanced → Transfer project → 選群組
權限角色能幹嘛（由高到低）
Owner群組一切管理、刪除
Maintainer管理專案設定、合併權限、CI/CD 設定
Developerpush、開 MR、跑 pipeline（日常開發主力）
Reporter唯讀＋回報 issue
Guest只能看 issue 等最小權限
權限會向下繼承：群組權限自動套到底下所有子群組與專案—— 在群組層級加一個 Developer，底下每個專案都是 Developer。要「例外」時再到專案層覆寫。

2.7 Visibility：三種可見性

層級誰能看到建議用途
Private只有專案成員預設值、公司內部專案
Internal登入此 GitLab 實例的人自架環境「全公司可見」
Public任何人（含未登入）開源專案、作品集

自架 GitLab 時 Internal 超好用：整個公司可看，公司外看不到——GitHub 沒有這個層級。

2.8 Worked Example：完成一次完整循環

任務 · TASK
1. 建立私有專案 demo-app（含 README）
2. clone 到本機
3. 新增 hello.py
4. commit + push
5. 在網頁確認檔案出現
驗收 · CHECKLIST

✅ git clone 成功
✅ git push 成功
✅ 網頁 Files 頁看到 hello.py
✅ git log --oneline 有兩筆 commit
✅ git remote -v 指向 gitlab.com

2.9 練習

  • 建立一個群組，在裡面建立兩個專案，練習權限繼承。
  • 把專案 visibility 依序改成 Public → Private，觀察網頁警告。
  • 用 git remote add 方式把一個既有資料夾推到 GitLab。
看完這單元你應該能說出：
  • 說出 Project 與 Group 各自對應 GitHub 的什麼概念，以及 Subgroup 的用途。
  • 在網頁上建立一個新的空白專案並選對 visibility。
  • 用 git clone 取得專案、修改後 add / commit / push 回 GitLab。
  • 從零用 git init + remote add 把既有資料夾推上 GitLab。
  • 建立群組並把專案放進群組，說出群組權限的層級關係。

進階真實情境 Worked Example

情境：建立多專案群組並用 Group Runner 自動化 CI

一個 15 人團隊，需要三個專案（前端、後端、共用函式庫），全部放在同一個群組下，共用一組自架 Runner。

群組架構 · GROUP TREE
myorg/                     ← Group
├── frontend-app           ← Project（Visibility: Private）
├── backend-api            ← Project（Visibility: Private）
├── shared-ui-lib          ← Project（Visibility: Internal，全公司可讀）
└── myorg.gitlab.io        ← Project（Visibility: Public，對外入口）

# Group Runner 註冊（在群組設定頁取得 token）
sudo gitlab-runner register \
  --url https://gitlab.example.com \
  --token <GROUP_TOKEN> \
  --executor docker \
  --tag-list "myorg" \
  --run-untagged="false"

# 權限設計：
# Owner → 技術主管（2人）
# Maintainer → Team Lead（3人）
# Developer → 開發者（10人）
設計決策：① 共用函式庫設 Internal 讓公司內其他團隊可讀但不能改；② Runner 用 tag 過濾，只有 myorg 群組的專案才能使用此 Runner；③ 權限向下繼承：在 Group 設 Developer，三個專案自動都是 Developer。

深入原理擴充

Namespace 與路由解析

GitLab 的 URL 路徑對應到內部的 Namespace（命名空間）。一個專案的完整路徑是 namespace/project，其中 namespace 可以是 User 或 Group。

URL 路徑Namespace 類型專案歸屬
gitlab.com/alice/helloUser（alice）個人專案
gitlab.com/myorg/backend-apiGroup（myorg）群組專案
gitlab.com/myorg/platform/backend-apiSubgroup（myorg/platform）子群組專案
容易搞錯：Transfer 專案到新群組時，所有 clone URL 會變——已通知團隊更新 remote，否則下次 push 會失敗。

診斷式疑難排解表

症狀可能原因解決方案
git push 顯示「remote: The project you were looking for could not be found」遠端 URL 路徑錯誤（例如群組名拼錯）執行 git remote -v 確認 URL，用 git remote set-url origin 修正
看不到 Internal 專案你在 GitLab.com（非自架），或帳號未登入Internal 只在自架環境有效；確認已登入該 GitLab 實例
Subgroup 裡的專案權限不符預期Subgroup 有獨立的權限設定，覆蓋了上層 Group 的繼承檢查 Subgroup → Members，確認是否有人為覆寫
git clone 报 SSL certificate problem自架 GitLab 使用自簽憑證，本機不信任執行 git config --global http.sslVerify false（開發用），或匯入公司 CA 憑證
專案路徑中有大寫字母被拒絕GitLab slug 只允許小寫英文、數字、連字號、底線專案名稱可含大寫，但路徑 slug 會自動轉小寫；建專案時直接用小寫命名

進階挑戰題

  1. 群組權限例外設計：一個 30 人的群組中，有 2 個專案需要「外部承包商」也能 push（Developer），但承包商不能看到其他專案。設計權限方案並說明如何用 Subgroup 或專案層級覆寫達成。
  2. 從 GitHub 遷移到 GitLab：描述完整遷移步驟（含 Issues、MR、Label），並列出三個遷移後需要檢查的項目（CI 設定、Webhook、Protected Branches）。

專案級端到端 Worked Example

情境：新產品線群組建置專案（my-company）

公司成立「平台」與「產品」兩條產品線，需要一次建好群組樹、權限矩陣與 Visibility 策略，讓 20 人團隊各自安全進場。

群組樹與專案 · GROUP TREE
my-company/                    ← Group（Private）
├── platform/                  ← Subgroup：平台工程
│   ├── api-gateway/           ← Project（Private）
│   ├── user-service/          ← Project（Private）
│   └── shared-libs/           ← Project（Internal）
├── product/                   ← Subgroup：產品開發
│   ├── web-app/               ← Project（Private）
│   └── mobile-app/            ← Project（Private）
└── my-company.gitlab.io/      ← Project（Public）對外入口（單元 7）
關鍵檔案 · KEY FILES
# .gitignore（每個新專案起手式，防密鑰入庫）
.env
*.pem
*.key
node_modules/
dist/
.DS_Store

# .gitlab-ci.yml（每個專案最基礎的 CI，單元 6）
stages: [test]
hello:
  stage: test
  script: echo "Hello from $CI_PROJECT_PATH"
驗證命令與輸出 · VERIFY
$ git remote -v
origin  git@gitlab.example.com:my-company/platform/api-gateway.git

$ glab api "groups/my-company" 2>/dev/null | head -c 300
{"id":7,"name":"my-company","visibility":"private",...}

$ git push -u origin main        # 首次推送後，網頁看到 pipeline 綠燈
To gitlab.example.com:my-company/platform/api-gateway.git
 * [new branch]      main -> main
專案級收斂：單元 2 的「Group / Subgroup / Visibility / 權限」在這裡變成一份群組樹＋一份權限矩陣——管理者照著建，20 人就能同時安全地進場工作。

效能 / 品質 / 安全深度

效能：讓 repo 保持輕量

  • clone 速度：大型二進位檔改用 Git LFS；設定檔案大小上限（push rule），防止有人推 500MB 的 log。
  • 歷史瘦身：定期 git gc，必要時用 git filter-repo 清掉誤入的大檔與敏感檔。
  • 避免單體巨庫：超過一個大型專案時用 Subgroup 拆成多個 Project，CI 與權限都好管理。

品質：專案標準化

  • 每個新專案從「樣板」建立：README + LICENSE + CHANGELOG + .gitignore + 基礎 .gitlab-ci.yml 一次給齊。
  • GitLab 專案樣板可直接選（Ruby/Node/Python 等），或自建群組樣板 group/project-templates 統一規範。

安全：權限最小化與可見性稽核

  • 權限矩陣：Owner 僅 2 人、Maintainer 各 Lead、Developer 開發者；Guest 只給需要看 issue 的外部人員。
  • Visibility 稽核：定期列出全部專案與 visibility，確認沒有誤設 Public 的內部專案。
  • Secret 防線：.gitignore + push rules 拒 .env/*.pem；密鑰一律走 CI/CD Variables。
