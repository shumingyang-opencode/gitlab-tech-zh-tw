2.1 術語先導：Project / Group / Subgroup

GitLab 不用「Repository」，改用專案（Project）與群組（Group）：

GitLab 術語GitHub 對應說明
Project（專案）Repository程式碼＋Issues＋CI＋Pages 的容器
Group（群組）Organization組織多個專案、集中管理權限與共用 Runner
Subgroup（子群組）—（GitHub 無對等）群組可巢狀，做出組織樹
Namespace（命名空間）owner 名專案路徑的第一段：group/project 或 user/project
為什麼叫 Project：GitLab 認為專案不只是「程式碼」—— 還含 Issues、CI/CD、容器庫、Pages，所以叫專案比叫 repo 更貼近它「完整產品單位」的定位。
路徑解讀：網址 gitlab.com/team-ai/backend/api-gw 中， team-ai 是 Group，backend 是 Subgroup，api-gw 才是 Project。

2.2 流程一：建立專案

網頁操作 · WEB UI
1. 右上角「＋」→ New project → Create blank project
2. Project name：hello-world（自動生成 slug）
3. Visibility：Private（先選這個，可事後改）
4. 勾選 Initialize repository with a README
5. 可選 .gitignore 樣板、LICENSE 樣板
6. Create project
新手常踩：把 visibility 設成 Public 以為無所謂—— 程式碼會公開給全世界（含未登入者）。不確定就先 Private，之後隨時可改。

2.3 流程二：Clone 到本機

命令 · COMMANDS
git clone https://gitlab.com/USER/hello-world.git
cd hello-world
git remote -v          # 確認 origin
結果 · RESULT
hello-world/
├── .git/          # 版本歷史（本地）
└── README.md      # 剛勾選產生的檔案

2.4 流程三：改檔 → 提交 → 上傳

Git 的日常循環與 GitHub 完全一樣（Git 是同一套工具）：

日常循環 · THE LOOP
git add .
git commit -m "說明這次改動"
git push
習慣養成：commit 訊息寫「做了什麼」而不是「改了檔案」—— git log --oneline 一眼看懂歷史，未來的人（包括三個月後的你）會感謝你。

2.5 流程四：從零推送既有資料夾

本機已經有專案、GitLab 上只有空白專案時：

首次推送 · FIRST PUSH
cd /path/to/my-app
git init -b main                     # 或 git init 後 git branch -M main
git add .
git commit -m "first commit"
git remote add origin https://gitlab.com/USER/hello-world.git
git push -u origin main              # -u 記憶 upstream，之後直接 git push
權限錯誤 403/denied 時：多半是認證問題。改用 SSH（git@gitlab.com:...git） 或確認 PAT scope 勾了 write_repository，而不是把 URL 改來改去。

2.6 Group 群組：組織專案

多個專案該放進群組管理：

建立群組 · GROUP
左上角選單 → Groups → New group
├── Group name：my-company
└── 建立後可在 Groups 內再建 Subgroup
    （如 my-company / frontend）

把既有專案移入：Project → Settings → General
  → Advanced → Transfer project → 選群組
權限角色能幹嘛（由高到低）
Owner群組一切管理、刪除
Maintainer管理專案設定、合併權限、CI/CD 設定
Developerpush、開 MR、跑 pipeline（日常開發主力）
Reporter唯讀＋回報 issue
Guest只能看 issue 等最小權限
權限會向下繼承：群組權限自動套到底下所有子群組與專案—— 在群組層級加一個 Developer，底下每個專案都是 Developer。要「例外」時再到專案層覆寫。

2.7 Visibility：三種可見性

層級誰能看到建議用途
Private只有專案成員預設值、公司內部專案
Internal登入此 GitLab 實例的人自架環境「全公司可見」
Public任何人（含未登入）開源專案、作品集

自架 GitLab 時 Internal 超好用：整個公司可看，公司外看不到——GitHub 沒有這個層級。

2.8 Worked Example：完成一次完整循環

任務 · TASK
1. 建立私有專案 demo-app（含 README）
2. clone 到本機
3. 新增 hello.py
4. commit + push
5. 在網頁確認檔案出現
驗收 · CHECKLIST

✅ git clone 成功
✅ git push 成功
✅ 網頁 Files 頁看到 hello.py
✅ git log --oneline 有兩筆 commit
✅ git remote -v 指向 gitlab.com

2.9 練習

  • 建立一個群組，在裡面建立兩個專案，練習權限繼承。
  • 把專案 visibility 依序改成 Public → Private，觀察網頁警告。
  • 用 git remote add 方式把一個既有資料夾推到 GitLab。
看完這單元你應該能說出：
  • 說出 Project 與 Group 各自對應 GitHub 的什麼概念，以及 Subgroup 的用途。
  • 在網頁上建立一個新的空白專案並選對 visibility。
  • 用 git clone 取得專案、修改後 add / commit / push 回 GitLab。
  • 從零用 git init + remote add 把既有資料夾推上 GitLab。
  • 建立群組並把專案放進群組，說出群組權限的層級關係。
