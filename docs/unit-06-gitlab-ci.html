6.1 什麼是 CI/CD

CI（持續整合）：每次 push 就自動建置＋測試，及早抓壞； CD（持續交付/部署）：驗證通過後自動部署到對應環境。 GitLab 把整套 CI/CD 內建——寫一個 .gitlab-ci.yml，push 就自動跑。

GitLab 的招牌：不必另接 Travis / Jenkins / CircleCI。 CI 是產品的一等公民，MR 頁直接內嵌 pipeline 結果。

6.2 核心概念

名詞意義類比
Pipeline一次完整的 CI/CD 流程（由 stages 組成）一整條生產線
Stage流程階段，依序執行工作站
Job實際執行的任務，屬於某個 stage工作站上的工序
Runner執行 job 的機器工人
Artifactjob 產出物（可傳給下一 stage）半成品
Variable環境變數（機密放 CI/CD variables）作業規範
執行規則：同一 stage 的 job 可平行跑；stage 之間 依序（前一 stage 全成功才進下一 stage）。任一 job 失敗 → pipeline 變紅。

6.3 .gitlab-ci.yml 結構

放在專案根目錄。最簡單的骨架：

.gitlab-ci.yml
stages:
  - build
  - test
  - deploy

build-app:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]

test-app:
  stage: test
  image: node:20
  script:
    - npm test
  needs: [build-app]

deploy-app:
  stage: deploy
  script:
    - echo "deploying to prod"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
解讀：push 後建一條 pipeline → build 先跑（產出 dist/ 當 artifact） → test 依賴 build（needs 可跳過 stage 順序）→ 只有 main 分支才 deploy。

6.4 stages 與 job 的執行順序

  • 預設 stage 順序：build → test → deploy（未寫 stages 時）。
  • 自訂 stages 決定順序；省略 stage 的 job 會跑到 test。
  • DAG：用 needs: 讓 job 不等整個 stage，只等它依賴的 job——大幅加速大型 pipeline。

6.5 Runners：執行機器

GitLab 本身不執行 job，需要 Runner：

Runner 類型 · RUNNERS
Shared runners     # GitLab.com 提供，免費額度有限（分鐘計）
Group runners      # 整個群組共用
Specific runners   # 專屬機器，可用 tags 指定

# 自架 GitLab 安裝 runner：
sudo gitlab-runner register
  # URL + registration token（群組/專案取得）
  # executor：shell / docker / kubernetes
自架 runner 的意義：測試機、內網服務、GPU、公司內部套件—— 都能用「自己的機器」當 runner。對自架 GitLab 而言這是標準配備，也是「程式碼不出公司」的最後一哩。

6.6 Artifacts 與 Cache

機制目的範例
Artifact把產出傳給之後的 job，或留給人下載編譯檔、測試報告、Pages 的 public/
Cache加速依賴安裝（同 job 重跑時重用）.npm/、pip cache、vendor/bundle
關鍵字 · KEYWORDS
artifacts:
  paths: [dist/]          # 產出目錄
  expire_in: 1 week        # 保留期限
  when: on_success

cache:
  key: $CI_COMMIT_REF_SLUG  # 依分支分開快取
  paths: [.npm/]
別搞混：artifact 是「產出給後面的用」，cache 是「加速自己的安裝」。 cache 不保證可用（可能被清），artifact 是保證可下載的。

6.7 Variables 與內建 CI_* 變數

機密值（金鑰、token）放 Settings → CI/CD → Variables，不寫進 YAML：

使用變數 · VARIABLES
# 設定：Settings → CI/CD → Variables
# DEPLOY_TOKEN（勾 Masked → 日誌中自動遮罩）

deploy-job:
  script:
    - curl -H "Authorization: Bearer $DEPLOY_TOKEN" ...
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" && $DEPLOY_ENABLED == "true"'

常用內建變數：$CI_COMMIT_SHA（commit）、$CI_COMMIT_BRANCH（分支）、 $CI_MERGE_REQUEST_IID（MR 編號）、$CI_JOB_NAME、$CI_PROJECT_PATH。

絕對不要 echo $SECRET：即使 Masked 也可能從日誌洩漏 變數值（例如在 URL 或錯誤訊息中）。機密一律只用在「不印出」的地方。

6.8 rules / only / when

  • rules: 現代的條件控制（多條件可用 and / ||），優先使用。
  • only/except 舊語法，較死板，新專案建議用 rules。
  • when: on_success / on_failure / always / manual：控制執行時機，manual 可做「手動部署按鈕」。

6.9 Worked Example：完整 pipeline 範例

.gitlab-ci.yml · SOURCE
stages: [build, test, deploy]

build-job:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]

test-job:
  stage: test
  image: node:20
  script:
    - npm test
  needs: [build-job]

deploy-staging:
  stage: deploy
  image: node:20
  script:
    - npm ci
    - npm run deploy:staging
  environment: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'

deploy-prod:
  stage: deploy
  script:
    - echo "release to prod"
  environment: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual     # 手動按鈕才部署正式
Pipeline · RENDERED

build → build-job（npm ci + build，存 dist/）

test → test-job（依賴 build-job，npm test）

deploy → deploy-staging（develop 分支）
         → deploy-prod（main 分支，manual 手動觸發）

develop 自動上 staging，main 需人工批准才上 production——常見的「環境階梯」。

6.10 把 CI 接上 MR 門檻

MR 上會直接顯示 pipeline 結果（✔ / ✘）。結合保護分支勾選「Pipelines must succeed」， CI 沒過就不能合併——品質的第一道自動防線（複習單元 4）。

6.11 練習

  • 為你的專案加一份最小 .gitlab-ci.yml（兩個 job），push 觀察 pipeline 跑起來。
  • 故意讓測試失敗一次，看 MR 上 pipeline 變紅、Merge 被擋。
  • 練習 rules: if 只在 main 部署，並加入一個 when: manual job。
看完這單元你應該能說出：
  • 說出 Pipeline / Stage / Job / Runner / Artifact 五個名詞的關係。
  • 從零寫出一份最小的 .gitlab-ci.yml（stages + 兩個 job）。
  • 用 rules: if 搭配 CI_* 內建變數做條件控制（例如只在 main 部署）。
  • 用 artifacts 傳遞產出物、用 cache 加速，並說明兩者差別。
  • 解釋自架 runner 的意義，並把 CI 設成 MR 的合併門檻。

進階真實情境 Worked Example

情境：多環境部署 + Review App + 手動生產部署

一個 Node.js 應用，需要：develop 分支自動部署到 staging 環境，每個 MR 自動產生一個 Review App（臨時預覽站），main 分支手動批准後才部署到 production，並在部署後自動執行 smoke test。

.gitlab-ci.yml · FULL PIPELINE
stages:
  - build
  - test
  - review
  - deploy
  - smoke

variables:
  DOCKER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG

build-job:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]
  cache:
    key: $CI_COMMIT_REF_SLUG
    paths: [node_modules/]

test-job:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test
    - npm run lint
  needs: [build-job]

review-app:
  stage: review
  image: node:20
  script:
    - npm ci --production
    - PORT=3000 node dist/server.js &
    - echo "Review app at http://$CI_ENVIRONMENT_SLUG.$CI_PROJECT_NAME.example.com"
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: http://$CI_ENVIRONMENT_SLUG.$CI_PROJECT_NAME.example.com
    on_stop: stop-review
  rules:
    - if: '$CI_MERGE_REQUEST_IID'

stop-review:
  stage: review
  script:
    - echo "Stopping review app for $CI_COMMIT_REF_SLUG"
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
  when: manual

deploy-staging:
  stage: deploy
  script:
    - echo "Deploying to staging..."
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'

deploy-prod:
  stage: deploy
  script:
    - echo "Deploying to production..."
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual

smoke-test:
  stage: smoke
  script:
    - curl -sf https://app.example.com/health || exit 1
    - echo "Smoke test passed"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
  needs: [deploy-prod]
設計決策：① Review App 搭配 environment.on_stop 實現 MR 合併後自動清理；② deploy-prod 用 when: manual 做人工批准門檻；③ smoke-test 用 needs 確保只在 prod 部署完成後才跑；④ cache 用分支 slug 分開，避免不同分支的依賴互相污染。

深入原理擴充

Runner Executor 差異與選擇

GitLab Runner 支援多種 executor，決定 job 在什麼環境中執行：

Executor運作方式優點缺點
shell直接在 Runner 主機上執行 shell 命令最簡單、最快job 間無隔離、污染主機環境
docker每個 job 啟動一個 Docker 容器隔離性好、可指定 image需要 Docker、稍慢（拉映像）
kubernetes每個 job 是一個 K8s Pod自動擴縮、適合大規模需 K8s 叢集、設定複雜
docker+machine動態建立 Docker 主機（auto-scaling）雲端 auto-scale需雲端 API、成本較高
選擇建議：小團隊用 docker（隔離＋彈性）；大型團隊或雲端環境用 kubernetes（自動擴縮）；CI 頻率低且主機乾淨時可用 shell（最省資源）。

DAG vs Stage 的執行模型

預設模式下，pipeline 依照 stage 順序執行——同一 stage 的 job 可平行，但下一 stage 必須等前一 stage 全部完成。DAG（Directed Acyclic Graph）用 needs: 打破此限制：

DAG vs Stage 視覺化
Stage 模式（嚴格順序）：
build ──→ test ──→ deploy
         （test 等 build 全部完成才開始）

DAG 模式（needs 控制）：
build-backend ──→ test-backend ──→ deploy
build-frontend ──→ test-frontend ↗
                  （test 只等自己的 build，不等別人）
注意：DAG 會讓 pipeline 圖形變成有向無環圖，不再是直條的 stage 欄位——理解這個差異對 debug pipeline 很重要。

診斷式疑難排解表

症狀可能原因解決方案
Pipeline 顯示「stuck」不動沒有匹配的 Runner（tag 不符、Runner 離線）Settings → CI/CD → Runners 檢查 Runner 狀態；確認 job 的 tag 與 Runner 的 tag 匹配
CI 變數在 job 中為空變數未設、scope 不符（如只設在專案但 job 在群組 Runner 跑）Settings → CI/CD → Variables 確認變數存在；檢查 Protected / Masked 設定是否限制了存取
cache 在不同 job 間不同步cache key 不同、或不同 Runner 實例沒有共享儲存確認 cache key 一致；若用 Docker executor 且多台 Runner，需設定共用 volume 或用 artifact 替代
Artifact 太大導致 pipeline 超時artifacts paths 包含 node_modules/ 或 .git/ 等大目錄縮小 artifacts 路徑；排除不必要目錄（用 exclude:）；設 expire_in 限制保留時間
rules: if 條件永遠不匹配變數名拼寫錯誤，或使用了不支援的 CI 變數在 job script 中先 echo $VARIABLE_NAME 確認變數值；參閱 GitLab CI/CD pre-defined variables 文件

進階挑戰題

  1. Pipeline 效能最佳化：一個有 20 個 job 的大型 pipeline，用 DAG（needs）重構 stage 順序，畫出「原本 stage 模式」與「DAG 模式」的執行時間對比圖，說明哪些 job 可以提早開始。
  2. CI 安全最佳實踐：列出 5 個防止 CI/CD 中密鑰洩漏的具體措施（含 Variable 設定、push rule、secret detection），並說明每個措施防堵的是什麼攻擊場景。
