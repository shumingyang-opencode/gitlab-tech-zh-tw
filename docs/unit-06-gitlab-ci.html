6.1 什麼是 CI/CD

CI（持續整合）：每次 push 就自動建置＋測試，及早抓壞； CD（持續交付/部署）：驗證通過後自動部署到對應環境。 GitLab 把整套 CI/CD 內建——寫一個 .gitlab-ci.yml，push 就自動跑。

GitLab 的招牌：不必另接 Travis / Jenkins / CircleCI。 CI 是產品的一等公民，MR 頁直接內嵌 pipeline 結果。

6.2 核心概念

名詞意義類比
Pipeline一次完整的 CI/CD 流程（由 stages 組成）一整條生產線
Stage流程階段，依序執行工作站
Job實際執行的任務，屬於某個 stage工作站上的工序
Runner執行 job 的機器工人
Artifactjob 產出物（可傳給下一 stage）半成品
Variable環境變數（機密放 CI/CD variables）作業規範
執行規則：同一 stage 的 job 可平行跑；stage 之間 依序（前一 stage 全成功才進下一 stage）。任一 job 失敗 → pipeline 變紅。

6.3 .gitlab-ci.yml 結構

放在專案根目錄。最簡單的骨架：

.gitlab-ci.yml
stages:
  - build
  - test
  - deploy

build-app:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]

test-app:
  stage: test
  image: node:20
  script:
    - npm test
  needs: [build-app]

deploy-app:
  stage: deploy
  script:
    - echo "deploying to prod"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
解讀：push 後建一條 pipeline → build 先跑（產出 dist/ 當 artifact） → test 依賴 build（needs 可跳過 stage 順序）→ 只有 main 分支才 deploy。

6.4 stages 與 job 的執行順序

  • 預設 stage 順序：build → test → deploy（未寫 stages 時）。
  • 自訂 stages 決定順序；省略 stage 的 job 會跑到 test。
  • DAG：用 needs: 讓 job 不等整個 stage，只等它依賴的 job——大幅加速大型 pipeline。

6.5 Runners：執行機器

GitLab 本身不執行 job，需要 Runner：

Runner 類型 · RUNNERS
Shared runners     # GitLab.com 提供，免費額度有限（分鐘計）
Group runners      # 整個群組共用
Specific runners   # 專屬機器，可用 tags 指定

# 自架 GitLab 安裝 runner：
sudo gitlab-runner register
  # URL + registration token（群組/專案取得）
  # executor：shell / docker / kubernetes
自架 runner 的意義：測試機、內網服務、GPU、公司內部套件—— 都能用「自己的機器」當 runner。對自架 GitLab 而言這是標準配備，也是「程式碼不出公司」的最後一哩。

6.6 Artifacts 與 Cache

機制目的範例
Artifact把產出傳給之後的 job，或留給人下載編譯檔、測試報告、Pages 的 public/
Cache加速依賴安裝（同 job 重跑時重用）.npm/、pip cache、vendor/bundle
關鍵字 · KEYWORDS
artifacts:
  paths: [dist/]          # 產出目錄
  expire_in: 1 week        # 保留期限
  when: on_success

cache:
  key: $CI_COMMIT_REF_SLUG  # 依分支分開快取
  paths: [.npm/]
別搞混：artifact 是「產出給後面的用」，cache 是「加速自己的安裝」。 cache 不保證可用（可能被清），artifact 是保證可下載的。

6.7 Variables 與內建 CI_* 變數

機密值（金鑰、token）放 Settings → CI/CD → Variables，不寫進 YAML：

使用變數 · VARIABLES
# 設定：Settings → CI/CD → Variables
# DEPLOY_TOKEN（勾 Masked → 日誌中自動遮罩）

deploy-job:
  script:
    - curl -H "Authorization: Bearer $DEPLOY_TOKEN" ...
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" && $DEPLOY_ENABLED == "true"'

常用內建變數：$CI_COMMIT_SHA（commit）、$CI_COMMIT_BRANCH（分支）、 $CI_MERGE_REQUEST_IID（MR 編號）、$CI_JOB_NAME、$CI_PROJECT_PATH。

絕對不要 echo $SECRET：即使 Masked 也可能從日誌洩漏 變數值（例如在 URL 或錯誤訊息中）。機密一律只用在「不印出」的地方。

6.8 rules / only / when

  • rules: 現代的條件控制（多條件可用 and / ||），優先使用。
  • only/except 舊語法，較死板，新專案建議用 rules。
  • when: on_success / on_failure / always / manual：控制執行時機，manual 可做「手動部署按鈕」。

6.9 Worked Example：完整 pipeline 範例

.gitlab-ci.yml · SOURCE
stages: [build, test, deploy]

build-job:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]

test-job:
  stage: test
  image: node:20
  script:
    - npm test
  needs: [build-job]

deploy-staging:
  stage: deploy
  image: node:20
  script:
    - npm ci
    - npm run deploy:staging
  environment: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'

deploy-prod:
  stage: deploy
  script:
    - echo "release to prod"
  environment: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual     # 手動按鈕才部署正式
Pipeline · RENDERED

build → build-job（npm ci + build，存 dist/）

test → test-job（依賴 build-job，npm test）

deploy → deploy-staging（develop 分支）
         → deploy-prod（main 分支，manual 手動觸發）

develop 自動上 staging，main 需人工批准才上 production——常見的「環境階梯」。

6.10 把 CI 接上 MR 門檻

MR 上會直接顯示 pipeline 結果（✔ / ✘）。結合保護分支勾選「Pipelines must succeed」， CI 沒過就不能合併——品質的第一道自動防線（複習單元 4）。

6.11 練習

  • 為你的專案加一份最小 .gitlab-ci.yml（兩個 job），push 觀察 pipeline 跑起來。
  • 故意讓測試失敗一次，看 MR 上 pipeline 變紅、Merge 被擋。
  • 練習 rules: if 只在 main 部署，並加入一個 when: manual job。
看完這單元你應該能說出：
  • 說出 Pipeline / Stage / Job / Runner / Artifact 五個名詞的關係。
  • 從零寫出一份最小的 .gitlab-ci.yml（stages + 兩個 job）。
  • 用 rules: if 搭配 CI_* 內建變數做條件控制（例如只在 main 部署）。
  • 用 artifacts 傳遞產出物、用 cache 加速，並說明兩者差別。
  • 解釋自架 runner 的意義，並把 CI 設成 MR 的合併門檻。
