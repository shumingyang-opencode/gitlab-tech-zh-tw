1.1 定義：GitLab 是什麼

GitLab 是一套單體（monolithic）DevOps 平台：它把程式碼託管、Merge Request、 Issues、CI/CD、容器登錄庫（Container Registry）、Pages、Wiki、監控、Secret 管理等原本散落各處的功能， 全部內建在一個產品裡。你不需要「GitHub + Travis + Docker Hub + Jira」四套服務拼裝—— GitLab 一個軟體就打算包辦軟體開發生命週期（SDLC）的每一段。

一句話：Git 是版本控制的「引擎」，GitLab 是把引擎連同 儀表板、產線、倉庫全部蓋進同一棟「車廠」的產品——而這棟車廠還能整棟搬回家自己經營。

1.2 與 Git、GitHub 的關係

很多人搞混這三者，其實層次非常清楚：

名稱是什麼層次
Git分散式版本控制工具（命令列），由 Linus 開發底層引擎
GitHub建在 Git 之上的代管平台＋開源社群生態平台（雲端優先）
GitLab建在 Git 之上的代管平台＋一體化 DevOps 產品平台（自架可）
關鍵：Git 指令在 GitHub 與 GitLab 上100% 相同—— 你換平台只是換「另一間托管 Git 的房子」，不需要重學版本控制。

1.3 一體化 DevOps 平台能幹嘛

GitLab 把整條開發流水線放進一個產品：

功能用途本站單元
Project 託管程式碼、版本歷史、保護分支單元 2
Merge Request合併請求、逐行 code review、批准規則單元 4
Issues / Boards / Milestones任務追蹤、看板、里程碑單元 5
CI/CD內建 pipeline：測試、建置、部署單元 6
Pages靜態網站部署單元 7
Container Registry內建 Docker 映像登錄庫（等同自帶 GHCR/Docker Hub）—
Secret / VariablesCI 變數、金鑰管理單元 6
監控 / 可觀測性內建錯誤追蹤、日誌、指標—
設計哲學：「單一應用程式」vs「拼裝多工具」。GitLab 的賣點是 深度整合：Issue 開著、MR 開著、pipeline 就在同一頁跑——資料不用在多套工具間搬運。

1.4 版本：社群版 vs 企業版 vs GitLab.com

版本授權說明
GitLab CE
Community Edition		MIT 開源社群版，完整開源、免費、可自架，核心功能都在
GitLab EE
Enterprise Edition		付費企業版，在開源核心上疊加：進階 approval rules、audit events、merge train、進階安全掃描
GitLab.comSaaS官方雲端服務，免費額度可用；付費方案解鎖 EE 功能
容易搞錯的點：CE 不是「閹割試用版」，而是完整的開源產品。 EE = 開源核心 + 企業功能附加包。這與「GitHub 本體閉源、只能付費用企業版」有本質差異。

1.5 託管模式：GitLab.com vs 自架

GitLab.com · 雲端
註冊帳號即可用
gitlab.com/USER/project

優點：零維護、開箱即用
限制：程式碼與 CI 在 GitLab 的雲
自架 · Self-managed
安裝在自家伺服器
gitlab.example.com/project

優點：資料完全留在公司
缺點：要自己維護升級

gitlab-ctl reconfigure   # 自架常用管理指令
選擇關鍵：法規（個資法、資安規範）要求「程式碼不得離境」時， 自架是主流解。GitLab 提供一鍵安裝包（Omnibus / Docker / Kubernetes）， 社群規模大，踩雷也有人分享。

1.6 帳號與認證

與 GitHub 相同，GitLab 支援 HTTPS + Personal Access Token（PAT）與 SSH key；另有官方 CLI glab。

認證方式 · AUTH
HTTPS + Personal Access Token   # 最常見，可設 scope 與期限
SSH key                          # 免密碼，放 ~/.ssh
glab auth login                  # GitLab CLI（類比 GitHub 的 gh）
git clone https://gitlab.com/USER/project.git
安全：Token 授權最小 scope、設定到期日、絕不 commit 進 repo； 一旦洩漏立即到 Settings → Access Tokens 撤銷。用「專案專用 token」比一把萬能 token 安全得多。

1.7 Worked Example：一個 commit 的旅程

流程 · SOURCE
git push origin feature-login
        │
        ▼
GitLab 收到 push
        │
        ├─ 更新程式碼與 commit 歷史
        ├─ 偵測新分支 → 提示 Create MR
        ├─ 觸發 CI pipeline（若有 .gitlab-ci.yml）
        │     build → test → deploy
        └─ 若關聯 issue → MR 合併後自動關閉
對應功能 · RENDERED

① git push → 程式碼託管
② 新分支提示 → Merge Request
③ pipeline 自動跑 → CI/CD
④ Closes #12 → Issues 自動化

一次 push，啟動整條 DevOps 流水線——這就是「一體化」的具體樣貌。

1.8 練習

  • 到 gitlab.com 註冊帳號。
  • 在「偏好設定」建立一個 Personal Access Token（scope 先只勾 read_repository）。
  • 用 glab auth login 或 HTTPS + PAT 完成一次 git clone。
  • 在網頁右上角「＋」→ New blank project，實際建立一個私有專案。

單元 2 · 第一個專案

進階真實情境 Worked Example

情境：選擇 GitLab 自架部署企業內部 DevOps 環境

一家受金融法規規範的科技公司，要求「所有原始碼與 CI/CD 流程不得離開公司網路」。團隊決定自架 GitLab CE，並在同一台主機安裝 GitLab Runner，使用 Docker executor 執行 CI jobs。

安裝流程 · DEPLOY
# 1. 安裝 Docker（Ubuntu）
sudo apt update && sudo apt install docker.io -y

# 2. 用 Docker 單鍵部署 GitLab CE
sudo docker run -d \
  --hostname gitlab.example.com \
  --name gitlab \
  -p 80:80 -p 443:443 -p 2222:22 \
  -v /srv/gitlab/config:/etc/gitlab \
  -v /srv/gitlab/logs:/var/log/gitlab \
  -v /srv/gitlab/data:/var/opt/gitlab \
  gitlab/gitlab-ce:latest

# 3. 等待啟動完成後，取得 root 初始密碼
sudo docker exec gitlab cat /etc/gitlab/initial_root_password

# 4. 註冊 Runner（群組層級，Docker executor）
sudo docker exec -it gitlab gitlab-runner register \
  --url https://gitlab.example.com \
  --token GROUP_REGISTRATION_TOKEN \
  --executor docker \
  --docker-image node:20

# 5. 驗證：在專案中建立 .gitlab-ci.yml，push 後觀察 pipeline
設計決策：① 用 Docker volume 掛載三個目錄確保資料持久化；② Runner 用 Docker executor 讓每個 job 在獨立容器中執行，互不污染；③ 2222 port 映射避免與主機 SSH 衝突。

深入原理擴充

GitLab 與 Git 的分工：伺服器端運作

Git 是命令列工具，GitLab 是 Rails 應用。GitLab 伺服器端透過 Gitolite 或自研的 Gitaly（gRPC 服務）管理 Git 倉庫的存取控制與操作。

元件職責容易誤解的點
GitalyGit 倉庫的 gRPC 存取層（clone、push、diff 等）GitLab 不是直接呼叫 git 命令列，而是透過 Gitaly 服務化
PraefectGitaly 代理，支援多副本與 failover這是 GitLab 14+ 的高可用方案，自架時預設不開啟
GitLab Shell處理 SSH 存取（push/pull）SSH 只是 Git 操作的通道，CI/CD 與 Web 操作不經 GitLab Shell
關鍵：你在 GitLab 網頁上看到的「儲存庫大小」包含 Git 物件、LFS、Wiki 等，但不含 CI artifacts 與 Container Registry——這兩者各有獨立儲存。

診斷式疑難排解表

症狀可能原因解決方案
git clone / push 報 403 ForbiddenPAT 未勾選 write_repository scope 或已過期到 Settings → Access Tokens 確認 scope 與到期日，重新產生 token
自架 GitLab 網頁打不開Docker port 映射錯誤，或主機防火牆擋住 80/443執行 docker ps 確認 port，檢查 ufw status 或 iptables 規則
SSH clone 報錯「Permission denied (publickey)」SSH key 未上傳到 GitLab，或本地 ssh-agent 未載入確認 ~/.ssh/id_rsa.pub 已加到 GitLab → Preferences → SSH Keys，並執行 ssh-add
git pull 後衝突標記未消失沒有實際執行 git add 與 git commit 解決衝突編輯衝突檔案 → git add . → git commit -m "resolve conflict"
Internal visibility 專案看不見使用 GitLab.com（非自架），Internal 級別不可用GitLab.com 只有 Public / Private；Internal 是自架專屬功能

進階挑戰題

  1. 多 Runner 策略設計：為一個有前端（Node）與後端（Python）的專案，設計 Runner tag 策略，讓前端 job 只跑在有 Node 環境的 Runner，後端 job 只跑在有 Python 的 Runner。畫出架構圖並說明 tag 的設定方式。
  2. GitLab CE vs EE 功能差距分析：調查三個 GitLab EE 獨有的功能（如 Audit Events、Merge Train、Code Owners），說明它們在 50 人以上的團隊中如何提升合規性與效率。
