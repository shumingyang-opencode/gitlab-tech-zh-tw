3.1 為什麼需要分支

分支（branch）是 Git 最強大的協作機制：每個人各自複製一條「工作線」開發， 互不干擾，最後再合併回去。main 永遠保持「可發布」的乾淨狀態， 新功能、修 bug 都先開分支做。

心智模型：main 是「出版中的正本」，feature 分支是「草稿」。 草稿寫完、校稿（review）通過，才正式併入正本。

3.2 分支操作（與 GitHub 相同）

常用指令 · COMMANDS
git checkout -b feature-login   # 建立並切換（= git branch + git checkout）
git switch feature-login        # 新版語法：切換
git branch                      # 列出分支（* 標示目前所在）
git push -u origin feature-login # 推分支到遠端並記住 upstream
git checkout main && git pull   # 回主分支並更新
命名慣例：feature/xxx、fix/xxx、chore/xxx。 GitLab 網頁還支援從 Issue 一鍵開分支：Create merge request and branch——分支名自動帶 issue 編號。

3.3 Merge Request 是什麼

Merge Request（MR）＝ GitHub 的 Pull Request（PR）—— 「請求把某分支合併進另一分支」的審查流程。名字不同，概念相同：不是直接 merge， 而是提出請求 → 隊友 review → 批准 → 合併。

MR 生命週期 · LIFECYCLE
開分支 → 開發 → commit → push
   → 發起 MR（source → target）
   → CI pipeline 自動跑（單元 6）
   → 隊友 Review / 留言 / Approve
   → 合併（或 squash / rebase）
   → 分支刪除、issue 自動關閉

3.4 開 MR 的兩種方式

方式一：push 後網頁提示

push 新分支後，GitLab 在「Branches」頁與「Merge requests」頁都會出現 Create merge request 提示——點下去 GitLab 已幫你填好 source/target。

方式二：Merge Requests 頁手動建立

操作 · WEB UI
專案 → Merge requests → New merge request
1. Source branch：feature-login（來源）
2. Target branch：main（目標）
3. 填標題與描述
4. 指派 Reviewers / Assignees
5. Create merge request

3.5 MR 描述與關聯 Issue

MR 描述 · DESCRIPTION
## 修正登入頁在 Safari 空白

- 加上欄位驗證
- 修正錯誤訊息樣式

## 測試
- [x] 手動測試 Safari 17
- [ ] 補單元測試

Closes #12

關鍵字 Closes / Fixes + #issue編號：MR 合併時自動關閉該 issue。 這是「Issue → MR → 合併 → 自動收尾」閉環的關鍵一步。

3.6 衝突處理 · Conflicts

當兩邊都改了同一行（或 Git 無法自動合併）就產生衝突。GitLab 會把 MR 標記為衝突狀態：

衝突標記 · MARKS
<<<<<<< HEAD
price = 100
=======
price = 120
>>>>>>> feature-x

手動解決流程：

  1. git checkout main && git pull 更新。
  2. git checkout feature-x && git merge main 合併並產生衝突。
  3. 編輯衝突檔，刪掉標記，保留正確內容（兩者都可能要留）。
  4. git add . → git commit → git push。
偷懶捷徑：簡單衝突可用 GitLab 網頁的 Resolve conflicts 按鈕直接改，不必開本機——但要小心改錯，複雜衝突還是本機處理。
減少衝突的好習慣：小 commit、頻繁 git pull、 一次只改一件事、避免大改版重寫同一批檔案。衝突大多不是技術問題，是「溝通與節奏」問題。

3.7 MR 的兩種常見目標分支

情境Target 分支說明
功能開發main / master日常最常見
版本發布release/1.0 等先併入 release 分支再發版
長期功能developgit-flow 類流程

GitLab 新專案主分支慣用 main；舊專案可能是 master——兩者只是名字。

3.8 Worked Example：完整開一顆 MR

命令 · COMMANDS
git checkout -b fix/typo
# 編輯 README 修正錯字
git add README.md
git commit -m "Fix typo in README"
git push -u origin fix/typo
# 網頁 → Create merge request
# 描述寫：Fixes #3
# Merge
驗收 · CHECKLIST

✅ MR 建立成功、target=main
✅ 描述含 Fixes #3
✅ pipeline 綠燈
✅ 合併後分支自動刪除
✅ Issue #3 自動關閉

3.9 練習

  • 開一個 feature/hello 分支，加一個檔案，push 後發 MR，再自己合併。
  • 製造一次衝突：兩個分支都改同一行，練習手動解衝突。
  • 在 MR 描述用 Closes #編號，合併後確認 issue 真的關了。
看完這單元你應該能說出：
  • 說出 MR 就是 GitLab 的「Pull Request」，並講出完整 MR 生命週期。
  • 用 git checkout -b 開分支、git push -u 推分支並在網頁發起 MR。
  • 用 Closes #12 / Fixes #12 讓 MR 合併時自動關閉 issue。
  • 讀懂衝突標記（<<<<<<< / ======= / >>>>>>>）並手動解決，或使用網頁 Resolve conflicts。
  • 解釋「小 commit、頻繁 pull」如何減少衝突。

進階真實情境 Worked Example

情境：GitFlow 工作流——多分支長期專案

一個 SaaS 產品同時維護三個版本（v1.x、v2.x、v3.x），需要 develop、release、hotfix 等分支策略。

GitFlow 分支圖 · FLOW
main ─────●────●────●─────────●───●───────────
          │    │    │         │   │
release/1  │    │    ●────●───┘   │           ← 釋出分支
           │    │    ↑    ↑       │
develop ───●────●────●────●────●──●───●───────
              ↑         ↑       ↑    ↑
feature/a ────●────●────┘       │    │
feature/b ──────────────────────●────┘
hotfix/1 ─────────────────────────────●──────  ← 緊急修復

# 1. 從 develop 開 feature
git checkout -b feature/search develop
# 開發完成 → MR target: develop

# 2. 準備發版：從 develop 開 release
git checkout -b release/2.1 develop
# 只做 bugfix → MR target: main + develop

# 3. 緊急修復：從 main 開 hotfix
git checkout -b hotfix/crash-fix main
# 修完 → MR target: main + develop
關鍵：hotfix 與 release 分支都需要「雙向合併」——合併到 main 後也要同步回 develop，否則下次 develop 的版本會缺少修復。

深入原理擴充

Git 合併策略的底層邏輯

Git 支援多種合併策略，影響衝突解決方式與歷史圖形：

策略指令特點何時使用
merge（預設）git merge branch產生合併 commit（兩條線匯合）保留完整開發過程
squash mergegit merge --squash branch把分支所有 commit 壓成一個歷史要乾淨
rebasegit rebase main把分支 commit「重放」到 main 最新位置，無合併節點直線歷史
黃金準則：永遠不要 rebase 已經 push 到遠端的分支——rebase 會改寫 commit hash，其他人的本地副本會產生分歧，導致混亂。只 rebase 你自己的、尚未分享的分支。

診斷式疑難排解表

症狀可能原因解決方案
git merge 報「CONFLICT (content)」但找不到衝突檔案衝突在子模組（submodule）或二進位檔中執行 git diff --name-only --diff-filter=U 列出所有衝突檔案
rebase 後 git push 被拒絕已 rebase 了已 push 的分支（歷史被改寫）確認沒其他人在此分支工作；若已推送需 git push --force-with-lease，並通知團隊
MR 合併後衝突又出現target 分支在 MR 開發期間又有新 commit，未 rebase/merge 最新 main在合併前先 git checkout feature && git rebase main，解決衝突後再 push
git log 圖形很亂、看不清分支關係大量 merge commit 造成交叉線執行 git log --oneline --graph --all；或改用 squash merge 減少合併節點
分支名稱含斜線（feature/login）本地切換失敗shell 把 / 當成路徑分隔符引用時加引號：git checkout "feature/login" 或用 git switch feature/login

進階挑戰題

  1. 衝突解決演練：建立一個模擬場景——main 上的 README.md 第 5 行改了，你的分支上同一行也改了。練習用 git mergetool（非編輯器手動解）解決衝突，比較兩種方式的效率。
  2. 分支策略選型：為一個「每兩週發版、同時修 hotfix」的團隊設計分支策略，畫出 Git 圖形並說明 release 與 hotfix 的合併路徑。
