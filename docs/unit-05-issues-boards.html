5.1 Issues：任務與 Bug 的單元

與 GitHub 相同：一件事一張單、有編號（#12）、可留言、指派與標籤。 但 GitLab 的 Issue 與 MR 的整合更深（Closes、Boards、Milestone 全打通）。

Issue 寫法 · FORMAT
標題：登入頁在 Safari 上空白
描述：
  步驟：
  1. 開 Safari 到 /login
  2. 畫面空白
  預期：顯示表單
  實際：白畫面（console 有 500）
  環境：Safari 17, macOS 15
  標籤：bug, priority::high
Issue 品質決定協作品質：「畫面壞了」是無效 issue； 「步驟＋預期＋實際＋環境」是可複現、可驗收的 issue。寫好「重現步驟」是工程師的基本功。

5.2 Labels · 標籤

GitLab 內建常見預設標籤，也可自訂。特色是 scoped labels：

常見標籤 · LABELS
bug  feature  documentation
good first issue  help wanted

# Scoped labels：同一個字首只會掛一個
type::bug        type::feature
priority::high   priority::low
do::1（待辦）     do::2（進行中）  review   done
Scoped labels 的威力：一張 issue 只能有一個 priority::， 系統會自動排除衝突。這讓「篩選」與「看板欄位」可以靠標籤自動對應——GitLab 的工程團隊文化常見到 type:: / priority:: / do:: 三組字首。

5.3 Milestones · 里程碑

把 issue / MR 歸到一個里程碑，追蹤整體進度——GitLab 的獨特點是同時掛 issue 與 MR：

Milestone 範例 · EXAMPLE
v1.0 發布（2026-10-01）
  ├─ #10 修登入 bug（open）
  ├─ #12 新增搜尋（open）
  ├─ #15 文件（closed）
  └─ !34 搜尋後端（merged，自動計入）
  進度：2/4
特色：MR 合併後自動算進 milestone 進度——「這個版本做了什麼」 由資料自動回答，不用人工統計。

5.4 Issue Boards · 看板（Kanban）

類似 GitHub Projects，但更接近 Trello；欄位通常由 label 定義：

看板 · BOARD
┌─ To do ──┬─ Doing ──┬─ Review ──┬─ Done ──┐
│ #10      │ #12       │           │ #15     │
│ #16      │           │           │         │
└──────────┴───────────┴───────────┴──────────┘
   do::1       do::2       review      done
   （欄位由 scoped label 對應）
WIP Limit（進行中上限）：「Doing」欄可設上限（例如 3）—— 超過就代表團隊同時做太多。WIP limit 是 Kanban 的核心紀律，逼團隊一件做完再做下一件。
多個 Board：可依產品、依團隊建多個 board； 加上「依 milestone 篩選」的 view——大型專案可以做到「每週站會看板就更新」。

5.5 Weight · 工作量

Issue 可設 weight（工作量估算，如 1–5）。配上看板的 Total weight 可估算 sprint 負載；配對 milestone 可追蹤「這個版本總工作量剩多少」。

Weight 範例 · WEIGHT
#12 新增搜尋        weight: 3
#10 修登入 bug       weight: 1
#16 設定頁重構       weight: 5   # 大工程，拆細更好
里程碑總計：9，已完成 4
別太迷信數字：weight 是相對估算不是工時保證。 重點是讓「分派不均」與「範圍膨脹」現形，而不是精準預測時程。

5.6 Epics · 史詩（群組層級）

Epic 是群組層級的「大目標」，底下掛多個 issue——GitLab 特有（EE/付費才有完整功能）：

Epic 範例 · EXAMPLE
Epic：2026 上半年使用者體驗
  ├─ #20 新版登入
  ├─ #21 暗色模式
  ├─ #22 載入動畫
  └─ 進度由底下 issue 自動彙總

用 Epic 組織「大到一個 issue 裝不下」的工作，例如一整個季度的產品方向。

5.7 Wiki · 專案文件

每個專案內建 Wiki（Markdown 撰寫），適合長文件與 SOP，定位與 GitHub Wiki 相同。 可與 CI 結合做成「自動生成文件」。（本站型態就是「Docs-as-Code」的另一種做法。）

5.8 完整工作流 · The Loop

工作流 · WORKFLOW
1. 開 Issue（label + milestone + weight）
2. 從 Issue 一鍵開分支（feature/12-login-fix）
3. 開發 → push → 開 MR（Closes #12）
4. CI 跑（單元 6）→ 有人 Approve
5. 合併 → Issue 自動關閉、看板自動移動、
   milestone 進度自動更新
閉環的意義：Issue → MR → Closes → 看板/里程碑 全部連動。 管理者看板看到的就是最新事實，不必人工同步任何東西。

5.9 Worked Example：用看板管一個 sprint

設定 · SETUP
1. 建 milestone「sprint-14」
2. 開 5 張 issue（各帶 do::1）
3. 設 Board 欄：do::1 / do::2 / review / done
4. Doing 欄 wip limit = 3
5. 每天把「正在做的」拖到 do::2
驗收 · CHECKLIST

✅ 每張 issue 有 label + milestone
✅ 看板欄位與 label 對應
✅ Doing 不超過 3 張
✅ 合併 MR 後 issue 自動關、看板自動移

5.10 練習

  • 建立 3 張 issue，用 type:: / priority:: / do:: 標籤分類，再建看板把欄位對上。
  • 設 milestone 並觀察「MR 合併後進度自動跳」。
  • 給一張難度差異大的 issue 設 weight，比較實際花費時間。
看完這單元你應該能說出：
  • 寫出一張結構清楚的 Issue（含步驟、預期、實際、環境）。
  • 建立 label 並用 type:: / priority:: 等 scoped labels 統一命名。
  • 把 issue 與 MR 掛進 milestone，讀懂版本進度。
  • 建立 Issue Board 看板（欄位對應 label），並說明 wip limit 的意義。
  • 說明 weight、Epic、Wiki 在大型專案中的角色。

進階真實情境 Worked Example

情境：用 Issue + Milestone + Board 管理一個 Sprint

一個敏捷團隊每兩週一個 Sprint，需要從 Backlog 篩選工作、分配 weight、每日站會更新看板、Sprint 結束時統計完成率。

Sprint 設定 · SETUP
# 1. 建立 Milestone
Milestone: Sprint 2026-W34
  Duration: 2026-08-18 → 2026-08-29

# 2. 開 Issue（全部帶 label）
#101 加入搜尋 API         type::feature  priority::high   do::1  weight: 5
#102 修正登入 500 錯誤    type::bug      priority::high   do::1  weight: 2
#103 文件更新             type::doc      priority::low    do::1  weight: 1
#104 壓縮前端 bundle      type::chore    priority::medium do::1  weight: 3
#105 設定頁 RWD           type::feature  priority::medium do::1  weight: 3

# 3. 建 Board：欄位 = do::1 / do::2 / review / done
# 4. WIP limit：Doing（do::2）最多 3 張
# 5. Sprint 篩選：在 Board 上方 Filter 設 milestone = Sprint 2026-W34
每日站會：只看 Board 上 do::2（進行中）的卡片，確認是否有阻塞。Sprint 結束時在 Milestone 頁檢視「關閉的 issue / 總 issue」比率即為完成率。

深入原理擴充

Scoped Labels 的互斥機制

Scoped labels 是 GitLab 獨有的強大功能。當你在一個 issue 上加入 do::2（進行中），系統會自動移除同字首的 do::1（待辦）——實現「單選」效果。

字首都選項範例行為
do::do::1、do::2、review、done一張 issue 同時只能有一個 do:: 值
priority::priority::high、priority::low只能一個優先級
type::type::bug、type::feature只能一個類型
底層原理：GitLab 用 :: 作為 scoped delimiter。加入新 label 時，系統搜尋同字首都的既有 label 並自動移除。這讓 Board 的欄位拖曳、篩選器都可靠 label 自動對應，無需手動維護狀態。

診斷式疑難排解表

症狀可能原因解決方案
Issue 拖曳到 Board 新欄位後，label 沒有自動更新欄位對應的 label 名稱拼寫不完全一致（含空格或大小寫差異）到 Board 設定確認欄位對應的 label，確保與 issue 上的 label 完全相同
Milestone 進度沒有包含某個 MRMR 的 target 分支不在此 milestone 的專案，或 MR 未被合併確認 MR 已 merged 且 target 在同一專案；Milestone 只統計已合併的 MR
看板出現「幽靈卡片」——Issue 已關閉但仍顯示Board 設定未排除已關閉的 issue在 Board 篩選器加入 state=opened，或檢查 Board 是否設為「顯示所有」
Epic 進度百分比不正確Epic 底下的 issue 有的不在同一群組，或 weight 未設定Epic 只能追蹤同群組下的 issue；確認所有子 issue 都有設定 weight
多個 Board 之間的 issue 重複顯示Board 的 filter 設定重疊（例如一個按 milestone、一個沒篩選）為每個 Board 設明確的 filter（milestone + label），避免交叉顯示

進階挑戰題

  1. Issue 模板設計：為「Bug 報告」與「Feature Request」各設計一個 Issue 模板（放在 .gitlab/issue_templates/），說明模板中應包含哪些欄位（步驟、預期、實際、優先級、相關 MR）。
  2. Epic 與 Milestone 的差異分析：用一個「開發新會員系統」的例子，說明 Epic（長期目標）與 Milestone（短期交付）如何搭配使用，並畫出兩者的層級關係圖。

專案級端到端 Worked Example

情境：敏捷交付管理專案（agile-delivery）

一個每兩週發一次的敏捷團隊，要把「issue 品質、label 詞彙、看板、里程碑、weight」標準化，讓 Sprint 可重複、可衡量。

專案檔案樹 · TREE
agile-delivery/
├── README.md                     # 團隊工作流總覽
├── .gitlab/
│   └── issue_templates/
│       ├── bug.md                # 含步驟/預期/實際/環境
│       └── feature.md            # 含 acceptance criteria
├── docs/
│   ├── label-vocabulary.md       # Label 詞彙表（type::/priority::/do::）
│   ├── board-guide.md            # 看板使用指南（wip limit）
│   └── sprint-playbook.md        # Sprint 流程手冊
└── data/
    └── sprint-template.md        # 每週 Sprint 開場模板
關鍵檔案 · KEY FILES
# docs/label-vocabulary.md（摘錄）
type::bug | type::feature | type::chore
priority::high | ::medium | ::low
do::1（待辦）do::2（進行中）review | done
# Scoped label：同字首只能一個，看板欄位自動對應

# .gitlab/issue_templates/feature.md（摘錄）
## 使用者故事
As a ..., I want to ..., so that ...
## 驗收標準（Acceptance Criteria）
- [ ] 具體可勾選的條件 1
- [ ] 具體可勾選的條件 2
驗證命令與輸出 · VERIFY
$ glab issue list --label "do::2"          # 進行中的工作
!102  修正登入 500        do::2  priority::high  weight 2
!104  壓縮前端 bundle     do::2  priority::med   weight 3

$ glab issue list --milestone "Sprint-14" --per-page 50 | wc -l
6                       # 里程碑總張數

$ glab issue list --milestone "Sprint-14" --state closed | wc -l
4                       # 已關閉張數 → 完成率 4/6
專案級收斂：單元 5 的名詞（issue/label/milestone/board/weight/epic）在這裡變成「詞彙表 + 模板 + 手冊」——團隊照著用，站會看板就是最新事實，沒人需要人工統計。

效能 / 品質 / 安全深度

品質：issue 品質決定可交付品質

  • 模板強制「使用者故事 + 驗收標準」：做之前就知道「怎樣才算做完」。
  • Bug 模板強制「步驟/預期/實際/環境」：可複現才算有效 issue。
  • Definition of Done 寫進 sprint 手冊：合併 + 測試 + 文件 + 部署才算 done。

效能：看板紀律提升 throughput

  • WIP limit：Doing 欄設上限，逼團隊「做完一件再做下一件」——WIP 是吞吐量的敵人。
  • weight 讓分派不均與範圍膨脹現形：單張 weight 過大（如 5+）就拆細。
  • 用 do:: scoped label 驅動看板，拖曳卡片＝改 label，狀態不靠人工維護。

安全：資訊最小暴露

  • Guest 只能開 issue 不能看程式碼——外部回報與內部程式碼隔離。
  • 敏感資訊（客戶名、帳密）不要寫進 issue 標題；需要時用加密工具傳。
  • 標籤與里程碑也有可見性：Private 群組的 issue 不會外流。
