5.1 Issues：任務與 Bug 的單元

與 GitHub 相同：一件事一張單、有編號（#12）、可留言、指派與標籤。 但 GitLab 的 Issue 與 MR 的整合更深（Closes、Boards、Milestone 全打通）。

Issue 寫法 · FORMAT
標題：登入頁在 Safari 上空白
描述：
  步驟：
  1. 開 Safari 到 /login
  2. 畫面空白
  預期：顯示表單
  實際：白畫面（console 有 500）
  環境：Safari 17, macOS 15
  標籤：bug, priority::high
Issue 品質決定協作品質：「畫面壞了」是無效 issue； 「步驟＋預期＋實際＋環境」是可複現、可驗收的 issue。寫好「重現步驟」是工程師的基本功。

5.2 Labels · 標籤

GitLab 內建常見預設標籤，也可自訂。特色是 scoped labels：

常見標籤 · LABELS
bug  feature  documentation
good first issue  help wanted

# Scoped labels：同一個字首只會掛一個
type::bug        type::feature
priority::high   priority::low
do::1（待辦）     do::2（進行中）  review   done
Scoped labels 的威力：一張 issue 只能有一個 priority::， 系統會自動排除衝突。這讓「篩選」與「看板欄位」可以靠標籤自動對應——GitLab 的工程團隊文化常見到 type:: / priority:: / do:: 三組字首。

5.3 Milestones · 里程碑

把 issue / MR 歸到一個里程碑，追蹤整體進度——GitLab 的獨特點是同時掛 issue 與 MR：

Milestone 範例 · EXAMPLE
v1.0 發布（2026-10-01）
  ├─ #10 修登入 bug（open）
  ├─ #12 新增搜尋（open）
  ├─ #15 文件（closed）
  └─ !34 搜尋後端（merged，自動計入）
  進度：2/4
特色：MR 合併後自動算進 milestone 進度——「這個版本做了什麼」 由資料自動回答，不用人工統計。

5.4 Issue Boards · 看板（Kanban）

類似 GitHub Projects，但更接近 Trello；欄位通常由 label 定義：

看板 · BOARD
┌─ To do ──┬─ Doing ──┬─ Review ──┬─ Done ──┐
│ #10      │ #12       │           │ #15     │
│ #16      │           │           │         │
└──────────┴───────────┴───────────┴──────────┘
   do::1       do::2       review      done
   （欄位由 scoped label 對應）
WIP Limit（進行中上限）：「Doing」欄可設上限（例如 3）—— 超過就代表團隊同時做太多。WIP limit 是 Kanban 的核心紀律，逼團隊一件做完再做下一件。
多個 Board：可依產品、依團隊建多個 board； 加上「依 milestone 篩選」的 view——大型專案可以做到「每週站會看板就更新」。

5.5 Weight · 工作量

Issue 可設 weight（工作量估算，如 1–5）。配上看板的 Total weight 可估算 sprint 負載；配對 milestone 可追蹤「這個版本總工作量剩多少」。

Weight 範例 · WEIGHT
#12 新增搜尋        weight: 3
#10 修登入 bug       weight: 1
#16 設定頁重構       weight: 5   # 大工程，拆細更好
里程碑總計：9，已完成 4
別太迷信數字：weight 是相對估算不是工時保證。 重點是讓「分派不均」與「範圍膨脹」現形，而不是精準預測時程。

5.6 Epics · 史詩（群組層級）

Epic 是群組層級的「大目標」，底下掛多個 issue——GitLab 特有（EE/付費才有完整功能）：

Epic 範例 · EXAMPLE
Epic：2026 上半年使用者體驗
  ├─ #20 新版登入
  ├─ #21 暗色模式
  ├─ #22 載入動畫
  └─ 進度由底下 issue 自動彙總

用 Epic 組織「大到一個 issue 裝不下」的工作，例如一整個季度的產品方向。

5.7 Wiki · 專案文件

每個專案內建 Wiki（Markdown 撰寫），適合長文件與 SOP，定位與 GitHub Wiki 相同。 可與 CI 結合做成「自動生成文件」。（本站型態就是「Docs-as-Code」的另一種做法。）

5.8 完整工作流 · The Loop

工作流 · WORKFLOW
1. 開 Issue（label + milestone + weight）
2. 從 Issue 一鍵開分支（feature/12-login-fix）
3. 開發 → push → 開 MR（Closes #12）
4. CI 跑（單元 6）→ 有人 Approve
5. 合併 → Issue 自動關閉、看板自動移動、
   milestone 進度自動更新
閉環的意義：Issue → MR → Closes → 看板/里程碑 全部連動。 管理者看板看到的就是最新事實，不必人工同步任何東西。

5.9 Worked Example：用看板管一個 sprint

設定 · SETUP
1. 建 milestone「sprint-14」
2. 開 5 張 issue（各帶 do::1）
3. 設 Board 欄：do::1 / do::2 / review / done
4. Doing 欄 wip limit = 3
5. 每天把「正在做的」拖到 do::2
驗收 · CHECKLIST

✅ 每張 issue 有 label + milestone
✅ 看板欄位與 label 對應
✅ Doing 不超過 3 張
✅ 合併 MR 後 issue 自動關、看板自動移

5.10 練習

  • 建立 3 張 issue，用 type:: / priority:: / do:: 標籤分類，再建看板把欄位對上。
  • 設 milestone 並觀察「MR 合併後進度自動跳」。
  • 給一張難度差異大的 issue 設 weight，比較實際花費時間。
看完這單元你應該能說出：
  • 寫出一張結構清楚的 Issue（含步驟、預期、實際、環境）。
  • 建立 label 並用 type:: / priority:: 等 scoped labels 統一命名。
  • 把 issue 與 MR 掛進 milestone，讀懂版本進度。
  • 建立 Issue Board 看板（欄位對應 label），並說明 wip limit 的意義。
  • 說明 weight、Epic、Wiki 在大型專案中的角色。
