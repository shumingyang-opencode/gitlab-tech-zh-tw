4.1 MR 頁面結構

把 MR 變成「有審查、有批准、有門檻」的合併流程，是 GitLab 的強項——尤其 Merge Request Approvals 比 GitHub 更早內建、也更有彈性。

MR 頁面 · LAYOUT
┌──────────────────────────────────────┐
│ !12 修正登入頁       Open · 3 commits │
├──────────────────────────────────────┤
│ Overview   Commits   Changes   Pipelines │
│  └─ 描述（Closes #12）                │
│  └─ Reviewers / Assignees             │
│  └─ CI 狀態：✔ Pipeline passed        │
│  └─ Approval：✔ Approved by 2 人     │
│  └─ [Merge]（條件全滿足才亮）          │
└──────────────────────────────────────┘
與 PR 的關鍵差異：GitLab 的 MR 頁有「Pipelines」分頁（CI 結果內嵌） 與「Approvals」區塊（批准計數）——審查與自動化在同一頁整合。

4.2 建立 MR：完整步驟

  1. 確定 source（來源分支）與 target（目標分支）——別倒過來！
  2. 寫清楚標題：一句話說「做什麼」，如「修正登入頁空白」。
  3. 描述用模板結構：動機、改法、測試方式、Closes #issue。
  4. 指派 Reviewers（審查人）與 Assignees（負責人）。
  5. 標 label（可掛 milestone）。
  6. 確認 CI pipeline 跑起來並綠燈。

4.3 Code Review 與討論

「Changes」分頁可逐行檢視 diff，GitLab 的 review 流程比 GitHub 多幾個好用機制：

  1. 點行號旁的「＋」留言，可附建議修正（suggestion）——對方一鍵套用。
  2. 用「Start a review」先累積意見，最後一起送出，避免「留言轟炸」。
  3. 作者修正後 push，新 commit 自動進同一 MR。
  4. 討論解決後點「Resolve thread」把討論標成已解決。
Suggestion · 留言範例
@@ -10,3 +10,3 @@
-if (user.age > 18) {
+const isAdult = user.age >= 18;
+if (isAdult) {

# 用 Apply suggestion 一鍵套用
機制 · RESOLVE

① 行內留言（可附 snippet）
② Start a review 批次送出
③ Resolve thread 標記已解決
④ 未解決的 thread 會阻擋合併（可設定）

特色：resolve thread 讓「這問題解決了沒」變成可追蹤的狀態， 比 GitHub 純留言串更接近「可管理的討論」。

4.4 Merge Request Approvals · 批准機制

Approvals 規定「要幾個特定角色批准才能合併」——GitLab 最早內建此功能，規則很細：

Approval rules · 範例規則
專案 → Settings → Merge requests → Approval rules
├── 需要 2 個批准才能合併
├── 特定檔案（如 src/payments/）必須資深者批准
├── 批准人不能是自己
└── 新增 commit 後「重新批准」也可設
GitLab 的細緻之處：可針對某些路徑設不同批准人—— 例如改到金流相關程式碼，必須 CTO 批准。GitHub 需付費或靠第三方才做得到類似效果。

4.5 合併方式：squash · rebase · merge

方式commit 歷史何時用
Merge commit保留全部 commit + 一個合併節點想保留開發過程的每步
Squash commits壓成一個 commit功能分支一堆小 commit 時，合併後歷史乾淨
Rebase merge線性重放、無合併節點要求「直線歷史」的專案
Squash · 視覺化
合併前：wip1 → wip2 → fix-typo → feat
合併後（squash）：feat 完整功能    # 一個乾淨 commit

合併後（merge commit）：
main ────────●─────────
             ╲         ╱
feature  ●→●→●→●   # 保留下每個 commit
團隊決策：沒有唯一正解。多數團隊偏好 squash（歷史整潔）； 「每個 commit 都要能編譯」的團隊則用 merge commit。定下來就好，別每顆 MR 都換。

4.6 保護分支與 CI 門檻

保護分支防止直接 push 主分支、強制 MR 流程：

設定 · SETTINGS
專案 → Settings → Repository → Protected branches
├── 選 main
├── Allowed to merge：Maintainers
├── Allowed to push：No one（只能走 MR）
└── 勾選：Pipelines must succeed
           All discussions resolved
           + 需要 Approvals（見 4.4）
組合拳：「保護分支 + pipeline 必須過 + 討論全解決 + N 人批准」= 高品質合併門檻。 CI 沒過或討論沒解決，Merge 按鈕直接不亮。

4.7 進階：Merge Train / Merge when pipeline succeeds

  • Merge when pipeline succeeds：現在點合併，但等 pipeline 綠了才真的合併。
  • Merge train：多顆 MR 排隊依序合併、互測相容性，避免「最後一台壞了前面的全壞」。

4.8 Worked Example：打造高門檻 MR 流程

設定 · CONFIG
1. 保護 main：禁止直接 push
2. Approval rules：需要 1 位 maintainer 批准
   + src/payments/ 需 owner 批准
3. 勾選 Pipelines must succeed
4. 勾選 All discussions must resolve
5. 合併方式：Squash commits
結果 · RESULT

MR 合併條件：
✅ pipeline 綠
✅ 討論全解決
✅ 批准數夠
✅ 非作者本人
→ 任一不滿足，Merge 按鈕不亮

4.9 練習

  • 開一顆 MR，練習 Changes 分頁留言＋Apply suggestion。
  • 設定 2 人批准規則，觀察差一人時 Merge 按鈕狀態。
  • 用 squash 合併一顆「一堆小 commit」的 MR，比較合併前後歷史。
看完這單元你應該能說出：
  • 說出 MR 頁面四大區塊（Overview / Commits / Changes / Pipelines）各自用途。
  • 在 Changes 分頁逐行留言、使用 Start a review 與 resolve thread 管理討論。
  • 設定 Merge Request Approvals，並說明「依路徑指定批准人」的進階規則。
  • 比較 Merge commit、Squash、Rebase 三種合併方式並說出何時用哪種。
  • 設定保護分支並讓 CI pipeline 成為合併門檻。

進階真實情境 Worked Example

情境：多階段審查流程——金流專案的高門檻 MR

一個處理付款的專案，MR 必須通過「自動 CI 檢查 + 2 人批准 + 路徑審查」三重門檻，且金流相關檔案（src/payments/）需要 CTO 親自批准。

Approval Rules 設定 · CONFIG
# Settings → Merge requests → Approval rules
Rule 1:  需要 2 人批准（全專案）
Rule 2:  需要 1 人批准，限檔案 src/payments/**
         指定 approver: CTO（user_id: 1）

# Settings → General → Push rules
✓ Reject unsigned commits
✓ Reject secret files (.env, *.pem)

# Protected branches → main
✓ Allowed to merge: Maintainers
✓ Allowed to push: No one
✓ Pipelines must succeed
✓ All discussions must resolve
✓ 需要 2 個批准
流程：① 開發者開 MR → ② CI 自動跑 lint + 測試 + SAST 掃描 → ③ 兩位 Maintainer 在 Overview 頁批准 → ④ 若改到 src/payments/，系統自動要求 CTO 另外批准 → ⑤ 所有討論 resolve → ⑥ Merge 按鈕亮起。

深入原理擴充

GitLab SAST 與安全掃描的運作原理

GitLab 內建 Secure 功能，在 CI pipeline 中自動執行靜態應用程式安全測試（SAST）：

掃描類型原理產出
SAST分析原始碼的語法樹（AST），比對已知漏洞模式（如 SQL injection pattern）MR 頁顯示漏洞清單（severity + file + line）
Secret Detection用正則比對 API key、token、密碼等模式發現硬編碼密鑰會阻止合併
Dependency Scanning掃描 package.json / requirements.txt 等，比對 CVE 資料庫列出有已知漏洞的套件版本
Container Scanning掃描 Docker 映像層的 OS 套件漏洞CVE 列表 + 修復建議版本
運作細節：SAST 透過 GitLab 的 Analyzers（獨立 Docker 映像）執行，例如 Semgrep 或 Bandit。分析器跑完後產出 JSON 報告，GitLab 統一解讀並呈現在 MR 的 Security 頁籤。

診斷式疑難排解表

症狀可能原因解決方案
Merge 按鈕灰色、不亮CI pipeline 失敗、或未達批准門檻、或有未解決討論逐一檢查：Pipelines 頁是否綠燈、Approvals 是否夠數、Overview 頁是否有 unresolved thread
Suggestion 套用後程式壞了建議只改了一行，但上下文需要其他變更套用後務必在本機 npm test 或 make test 驗證，不要盲目套用
批准數「卡住」不會減少Settings 中沒勾「Remove all approvals when commits are added」到 Settings → Merge requests → 勾選該選項，確保新 commit 重置批准狀態
MR 頁看不到 Pipelines 分頁此專案沒有 .gitlab-ci.yml，或 pipeline 未觸發確認根目錄有 .gitlab-ci.yml 且 push 觸發了 pipeline
Squash 合併後 commit 訊息不符合規範預設 squash commit message 只帶 MR 標題在 Settings → Merge requests 設定 squash commit message 模板，例如帶 $TITLE + $MR_URL

進階挑戰題

  1. 自訂 MR 模板：在專案中建立兩個 MR 描述模板（bugfix template 與 feature template），說明如何在 .gitlab/merge_request_templates/ 目錄下建立，並在建立 MR 時從下拉選單選擇。
  2. Merge Train 模擬：說明 Merge Train 的運作流程：假設同時有 5 顆 MR 排隊合併到 main，畫出「依序合併 + 互相測試」的序列圖，並比較它與「每顆 MR 各自等 pipeline」在時間效率上的差異。

情境：合規金流平台 MR 專案（payments-platform）

處理付款的專案，MR 必須過「CI 全綠 + 2 人批准 + 討論全解決 + 金流路徑 CTO 批准 + 安全掃描無高風險」五重門檻。把單元 4 的 approval / 保護分支 / 合併方式與單元 6 的 CI 安全整合成一個專案。

# .gitlab-ci.yml（安全掃描段落，單元 6）

專案級收斂：「審查（單元 4）+ 安全（單元 6）」合成一座自動化品質閘門：人類只管「批准」，機器管「綠燈＋掃描」——合規靠制度，不靠記憶。

效能 / 品質 / 安全深度

品質：把 merge checks 當「合併契約」

  • 合併契約＝pipeline 綠 + 批准數夠 + 討論全 resolve + 路徑專屬批准——任一不滿足，Merge 不亮。
  • Merge train：多顆 MR 排隊依序合併並互測，避免「各自通過、合起來壞掉」。
  • squash commit message 用模板（$TITLE + MR 連結），讓歷史可回溯到審查。

安全：掃描自動化，漏洞擋在合併前

  • SAST 抓程式碼漏洞（SQL injection、XSS 模式）；Secret Detection 抓硬編碼密鑰；Dependency Scanning 比對 CVE。
  • Push rules：拒絕 .env / *.pem / *.key 上傳——從源頭擋密鑰入庫。
  • 安全報告進 MR 的 Security 頁籤，合併門檻可設「無 high/critical 才能合併」。

效能：讓合併排隊自動化

  • Merge when pipeline succeeds：現在點合併，綠了才執行——不用人盯。
  • Merge train 平行等待、依序測試，比「每顆 MR 各自等 pipeline」更省時間也更安全。
