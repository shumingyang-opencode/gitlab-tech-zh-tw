4.1 MR 頁面結構

把 MR 變成「有審查、有批准、有門檻」的合併流程，是 GitLab 的強項——尤其 Merge Request Approvals 比 GitHub 更早內建、也更有彈性。

MR 頁面 · LAYOUT
┌──────────────────────────────────────┐
│ !12 修正登入頁       Open · 3 commits │
├──────────────────────────────────────┤
│ Overview   Commits   Changes   Pipelines │
│  └─ 描述（Closes #12）                │
│  └─ Reviewers / Assignees             │
│  └─ CI 狀態：✔ Pipeline passed        │
│  └─ Approval：✔ Approved by 2 人     │
│  └─ [Merge]（條件全滿足才亮）          │
└──────────────────────────────────────┘
與 PR 的關鍵差異：GitLab 的 MR 頁有「Pipelines」分頁（CI 結果內嵌） 與「Approvals」區塊（批准計數）——審查與自動化在同一頁整合。

4.2 建立 MR：完整步驟

  1. 確定 source（來源分支）與 target（目標分支）——別倒過來！
  2. 寫清楚標題：一句話說「做什麼」，如「修正登入頁空白」。
  3. 描述用模板結構：動機、改法、測試方式、Closes #issue。
  4. 指派 Reviewers（審查人）與 Assignees（負責人）。
  5. 標 label（可掛 milestone）。
  6. 確認 CI pipeline 跑起來並綠燈。

4.3 Code Review 與討論

「Changes」分頁可逐行檢視 diff，GitLab 的 review 流程比 GitHub 多幾個好用機制：

  1. 點行號旁的「＋」留言，可附建議修正（suggestion）——對方一鍵套用。
  2. 用「Start a review」先累積意見，最後一起送出，避免「留言轟炸」。
  3. 作者修正後 push，新 commit 自動進同一 MR。
  4. 討論解決後點「Resolve thread」把討論標成已解決。
Suggestion · 留言範例
@@ -10,3 +10,3 @@
-if (user.age > 18) {
+const isAdult = user.age >= 18;
+if (isAdult) {

# 用 Apply suggestion 一鍵套用
機制 · RESOLVE

① 行內留言（可附 snippet）
② Start a review 批次送出
③ Resolve thread 標記已解決
④ 未解決的 thread 會阻擋合併（可設定）

特色：resolve thread 讓「這問題解決了沒」變成可追蹤的狀態， 比 GitHub 純留言串更接近「可管理的討論」。

4.4 Merge Request Approvals · 批准機制

Approvals 規定「要幾個特定角色批准才能合併」——GitLab 最早內建此功能，規則很細：

Approval rules · 範例規則
專案 → Settings → Merge requests → Approval rules
├── 需要 2 個批准才能合併
├── 特定檔案（如 src/payments/）必須資深者批准
├── 批准人不能是自己
└── 新增 commit 後「重新批准」也可設
GitLab 的細緻之處：可針對某些路徑設不同批准人—— 例如改到金流相關程式碼，必須 CTO 批准。GitHub 需付費或靠第三方才做得到類似效果。

4.5 合併方式：squash · rebase · merge

方式commit 歷史何時用
Merge commit保留全部 commit + 一個合併節點想保留開發過程的每步
Squash commits壓成一個 commit功能分支一堆小 commit 時，合併後歷史乾淨
Rebase merge線性重放、無合併節點要求「直線歷史」的專案
Squash · 視覺化
合併前：wip1 → wip2 → fix-typo → feat
合併後（squash）：feat 完整功能    # 一個乾淨 commit

合併後（merge commit）：
main ────────●─────────
             ╲         ╱
feature  ●→●→●→●   # 保留下每個 commit
團隊決策：沒有唯一正解。多數團隊偏好 squash（歷史整潔）； 「每個 commit 都要能編譯」的團隊則用 merge commit。定下來就好，別每顆 MR 都換。

4.6 保護分支與 CI 門檻

保護分支防止直接 push 主分支、強制 MR 流程：

設定 · SETTINGS
專案 → Settings → Repository → Protected branches
├── 選 main
├── Allowed to merge：Maintainers
├── Allowed to push：No one（只能走 MR）
└── 勾選：Pipelines must succeed
           All discussions resolved
           + 需要 Approvals（見 4.4）
組合拳：「保護分支 + pipeline 必須過 + 討論全解決 + N 人批准」= 高品質合併門檻。 CI 沒過或討論沒解決，Merge 按鈕直接不亮。

4.7 進階：Merge Train / Merge when pipeline succeeds

  • Merge when pipeline succeeds：現在點合併，但等 pipeline 綠了才真的合併。
  • Merge train：多顆 MR 排隊依序合併、互測相容性，避免「最後一台壞了前面的全壞」。

4.8 Worked Example：打造高門檻 MR 流程

設定 · CONFIG
1. 保護 main：禁止直接 push
2. Approval rules：需要 1 位 maintainer 批准
   + src/payments/ 需 owner 批准
3. 勾選 Pipelines must succeed
4. 勾選 All discussions must resolve
5. 合併方式：Squash commits
結果 · RESULT

MR 合併條件：
✅ pipeline 綠
✅ 討論全解決
✅ 批准數夠
✅ 非作者本人
→ 任一不滿足，Merge 按鈕不亮

4.9 練習

  • 開一顆 MR，練習 Changes 分頁留言＋Apply suggestion。
  • 設定 2 人批准規則，觀察差一人時 Merge 按鈕狀態。
  • 用 squash 合併一顆「一堆小 commit」的 MR，比較合併前後歷史。
看完這單元你應該能說出：
  • 說出 MR 頁面四大區塊（Overview / Commits / Changes / Pipelines）各自用途。
  • 在 Changes 分頁逐行留言、使用 Start a review 與 resolve thread 管理討論。
  • 設定 Merge Request Approvals，並說明「依路徑指定批准人」的進階規則。
  • 比較 Merge commit、Squash、Rebase 三種合併方式並說出何時用哪種。
  • 設定保護分支並讓 CI pipeline 成為合併門檻。
