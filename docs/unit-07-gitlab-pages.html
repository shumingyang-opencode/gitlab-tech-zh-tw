7.1 GitLab Pages 是什麼

GitLab Pages 把專案裡的靜態檔案直接變成網站——與 GitHub Pages 概念相同， 但部署完全由 CI/CD 驅動：你寫一個特殊的 pages job，GitLab 就把產出發布成網站。

一句話：Pages = 「CI 的產出 → 靜態網站」。所以它跟單元 6 密不可分—— 先懂 pipeline，Pages 就只是「其中一種 deploy job」。

7.2 URL 格式

部署後的網址 · URLS
專案頁（GitLab.com）：
  https://USER.gitlab.io/project-name/

使用者頁：
  https://USER.gitlab.io/
  （專案名必須是 USER.gitlab.io）

群組頁：
  https://GROUP.gitlab.io/
  （或 https://GROUP.gitlab.io/project/）

自架：
  https://pages.example.com/project/

7.3 啟用 Pages：pages job 三步驟

GitLab 找「名叫 pages 的 job」來發布網站，且 stage 固定 deploy，內容放 public/：

.gitlab-ci.yml · 純靜態站
pages:
  stage: deploy
  script:
    - mkdir -p public
    - cp -r index.html assets public/
  artifacts:
    paths:
      - public
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
三步驟：（1）job 名 pages；（2）把網站內容放進 public/；（3）用 artifacts 把 public 傳出去。pipeline 成功後 GitLab 自動發布。

7.4 需要建置的專案（框架）

用 Node 建置工具（Vite / Astro / Hugo）時，先在 job 裡 build 再搬進 public：

.gitlab-ci.yml · Vite 範例
image: node:20

pages:
  stage: deploy
  script:
    - npm ci
    - npm run build          # 產出 dist/
    - cp -r dist public
  artifacts:
    paths: [public]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
路徑注意：若 base 路徑不是根目錄，前端資源會 404。 Vite 需設 base: '/project-name/'；Astro 設 site 與 base——這是框架站最常見的坑。

7.5 群組頁 / 使用者頁

  • 使用者頁：建一個名為 USER.gitlab.io 的專案，放 index.html，pipeline 一跑即上線。
  • 群組頁：同理建 GROUP.gitlab.io 專案——可放公司入口、內部文件中心。

7.6 自訂網域與 SSL

在「Deploy → Pages」頁可設定：

  1. Custom domain：填 docs.example.com。
  2. 到 DNS 服務商加 CNAME docs.example.com → USER.gitlab.io。
  3. GitLab 自動申請 Let's Encrypt SSL（勾選 Auto SSL）。
  4. 可設 access control：只有專案成員能看（GitHub 無此功能）。
存取控制是賣點：自架環境的 Pages 可設「登入後才能看」—— 內部文件、暫存站點不用公開給全世界。

7.7 限制 · Limits

項目限制
內容靜態檔案（無後端邏輯）
大小每個 Pages 站有大小上限（視方案）
流量/建置免費方案有流量與 CI 分鐘上限
部署方式一定透過 CI（GitHub 可「deploy from branch」一鍵）

7.8 Worked Example：把這類教學站部署上線

專案結構 · SOURCE
my-docs/
├── index.html
├── docs/
│   └── unit-01.html
├── assets/
│   └── site.css
└── .gitlab-ci.yml

# 注意：資料夾「空目錄」Git 不會追蹤，
# 需放 .gitkeep 或直接在 job 裡 mkdir
部署 · RENDERED

① push → pipeline 啟動
② pages job 執行（複製 public/）
③ artifact 上傳
④ 網址：https://USER.gitlab.io/my-docs/
⑤ 之後每次 push 自動更新網站

7.9 常見錯誤與陷阱

陷阱清單：① job 不叫 pages → 不會發布； ② 內容不在 public/ 或沒用 artifacts 傳出 → 空站； ③ 框架 base 路徑沒設 → 資源 404； ④ rules 條件沒寫 → 每次 push 都部署（非 main 分支也會）； ⑤ 只部署了 main 卻忘了先 merge——先確認分支。

7.10 練習

  • 用純 HTML（index.html + css）部署出你的第一個 Pages 站。
  • 改用 Vite 建置流程，確認資源路徑正確。
  • 嘗試設定自訂網域（可先在本機 /etc/hosts 模擬）。

  • 說出 GitLab Pages 的三種網址格式（專案頁 / 使用者頁 / 群組頁）。
  • 寫出以 pages job + public/ + artifacts 部署靜態網站的 .gitlab-ci.yml。
  • 寫出框架專案（Node build）的 pages job 流程。
  • 設定自訂網域（CNAME）與 SSL，並列出 Pages 的限制。

進階真實情境 Worked Example

情境：Astro 框架 + 多環境部署 + 自訂網域

一個技術文件站用 Astro 製作，需要：PR 自動產生 Review App 供預覽、main 分支部署到生產環境、自訂網域 docs.example.com 並自動 SSL。

.gitlab-ci.yml · FULL DEPLOY
image: node:20

stages:
  - build
  - deploy

build:
  stage: build
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]

pages:
  stage: deploy
  script:
    - cp -r dist/* public/
  artifacts:
    paths:
      - public
  needs: [build]
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

review:
  stage: deploy
  script:
    - cp -r dist/* public/
  artifacts:
    paths:
      - public
  needs: [build]
  rules:
    - if: '$CI_MERGE_REQUEST_IID'
設計決策：① build stage 與 deploy stage 分離——build 失敗不會觸發 Pages 發布；② pages job 只在 main 分支跑，review job 只在 MR 跑，兩者互不干擾；③ Astro 的 astro.config.mjs 需設 site: 'https://docs.example.com' 與 base: '/'（自訂網域時 base 為根）。

深入原理擴充

GitLab Pages 的發布機制

GitLab Pages 不是「把檔案丟到 Web 伺服器」——它有獨立的發布管線：

步驟運作容易忽略的細節
① artifact 上傳CI 成功後，GitLab 把 public artifact 備份到 Pages 儲存artifact 必須包含 public 目錄，且 job 名必須是 pages
② 部署觸發GitLab Pages daemon 讀取 artifact，更新網站內容發布有延遲（通常 1-5 分鐘），不是 push 後立即上線
③ CDN 快取GitLab.com 的 Pages 有 CDN 快取層改 CSS/JS 後瀏覽器可能讀到舊版——需要清除快取或加 hash 後綴
④ 存取控制可設定「僅專案成員可見」自架 GitLab 的 Pages 可走內網，GitLab.com 的 Pages 預設公開
常見誤解：GitHub Pages 可以「從分支直接發布」（不需要 CI），GitLab Pages 一定要透過 CI 的 pages job。這是兩者最大的架構差異。

診斷式疑難排解表

症狀可能原因解決方案
Pages 部署後顯示 404job 名不是 pages，或 artifacts 路徑不含 public確認 .gitlab-ci.yml 中有 pages: job，且 artifacts paths 包含 public 目錄
CSS / JS 路徑 404（資源讀不到）Astro/Vite 的 base 路徑未設定，或設定為根目錄 / 但專案不是根域名Astro：base: '/project-name/'；Vite：base: '/project-name/'；自訂網域時 base: '/'
自訂網域 SSL 一直不生效DNS CNAME 尚未生效，或 GitLab 的 Auto SSL 尚未觸發用 dig docs.example.com 確認 CNAME 指向正確；等待 15-30 分鐘讓 Let's Encrypt 驗證
Pipeline 綠但 Pages 沒更新rules 條件限制了 pages job 只在特定分支跑，但你推到了其他分支確認 pages job 的 rules 是否包含你的分支；或暫時移除 rules 測試
Pages 站被搜尋引擎索引到不想公開的內容專案設為 Public，且無 robots.txt 控制在 public/ 加 robots.txt；或將專案改為 Private / Internal

進階挑戰題

  1. 多語言文件站部署：設計一個 Astro 多語言文件站的 Pages 部署方案，包含 /zh/ 與 /en/ 兩個語言版本，說明 Astro 的 i18n 設定與 Pages 的 URL 結構如何配合。
  2. Pages vs Cloudflare Pages vs Vercel 比較：從部署流程、自訂網域、SSL、存取控制、免費額度五個面向，比較 GitLab Pages 與兩大前端部署平台的差異，並說明何時選 GitLab Pages 更合適。
